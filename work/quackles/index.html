The constraint

The product page needed extremely high-resolution inspection while staying mobile-first, statically deployable on GitHub Pages, compatible with native scrolling and pinch behavior, and unwilling to let source resolution dictate browser memory.

The existence of a 200MP source should not cause the browser to request 200MP of detail.

The first useful architecture

At those revisions, the inspection path kept a small base hero for immediate display, then treated the high-resolution source as a demand-driven deep-zoom pyramid. Requested detail followed visible pixels × zoom and was capped by a device profile rather than by the maximum source tier.

  • 1,024 px base hero remained the initial surface.
  • The 11,584 × 17,376 master was published as a WebP DZI pyramid.
  • Progressive detail tiers reached 11,584 px only when inspection required them.
  • The tested mobile policy could cap decoded memory, compressed cache, concurrent jobs, zoom, source tier, overscan, and navigator resolution.

A naive path was intentionally rejected

An earlier direction would have used a second image surface for the navigator and kept the full sequence renderer subscribed to every camera spring frame. The PR implementation instead snapshotted the already-rendered base canvas for a zero-fetch viewfinder, moved camera transform ownership into the inspection compositor path, and only woke tile planning when target zoom/focus or inspection boundaries changed.

Visual QA found what state tests missed

The first CI screenshot exposed a mobile-only defect: during native pinch, the navigator was technically active but magnified and pushed offscreen with the poster. The fix counter-scaled the navigator and anchored it inside the active visual viewport. Acceptance at that revision checked that its rendered bounds stayed inside the viewport.

Verification became part of the design

The two historical PRs record exact-head evidence receipts rather than only implementation notes. At those heads, verification included lint, typecheck, static build, real Chromium inspection behavior, request quiescence, navigator behavior, reversible scroll/inspection ownership, and mobile capability fixtures.

Non-claims

The 200MP pyramid in PR #39 is specifically for Blue p0000000; it is not evidence that every product/theme asset has equivalent source detail. That PR also explicitly does not claim to solve the larger desktop/fullscreen and HQ-skinned-runtime redesign. These historical receipts do not certify later image variants, later zoom behavior, or current live-site performance.

Why this belongs in the portfolio

The interesting artifact is not the duck page by itself. It is the loop: ambitious interaction → device constraint → measurable failure → architecture change → browser-level evidence → explicit limitation. That is the same working style the rest of the portfolio system is being rebuilt to expose.
